# REGS 測試指南（Windows / PowerShell）

本文件說明如何在全新環境中啟動 REGS 系統，並依《期末專案說明》之評分基準，逐項驗證各功能是否正確運作。所有指令以 **Windows PowerShell** 為主。

本指南的驗證章節（第三至六節）刻意依《期末專案說明》評分表之四大分項編排，並於各小節標註對應配分，以利對照評分：

| 評分分項 | 配分 | 對應章節 |
|---------|:----:|---------|
| 自動化編譯管道 | 20 | 第三節 |
| 非同步任務隊列與併發控制 | 10 | 第四節 |
| 權限控管與查詢功能 | 20 | 第五節 |
| 文件 | 10 | 第六節 |

> **操作方式說明**：伺服器以背景容器執行，因此**單一 PowerShell 視窗即可**完成全部測試。
> 若需即時觀察伺服器日誌，可另開一個視窗執行 `docker compose logs -f app`。

## 一、測試環境準備（每台機器僅需執行一次）

### 1.1 前置需求

| 需求 | 說明 |
|------|------|
| Docker Desktop | 必須開啟並顯示 Engine running（工作列鯨魚圖示呈穩定狀態） |

僅此一項。**本機不需要安裝 Go、OpenSSL 或 psql**——編譯、金鑰生成、建表與判題全部在容器內完成。

### 1.2 啟動整套系統

```powershell
docker compose up -d --build
```

此單一指令會依序完成：

| 步驟 | 由誰執行 | 說明 |
|------|---------|------|
| 編譯 Go 伺服器 | `builder` 階段（`golang:1.25-alpine`） | 不需本機 Go |
| 生成 JWT 金鑰 | `keygen` 一次性容器 | 以容器內 OpenSSL 產生 EC P-256 金鑰對，存入 `keys` volume；已存在則保留 |
| 啟動 Postgres | `db` 服務 | 具 healthcheck，`app` 會等待其就緒 |
| 建立 / 更新資料表 | `app` 啟動時自動執行 | 內嵌之 `schema.sql`，語句皆為冪等，每次啟動皆會套用 |
| 拉取判題映像檔 | `app` 啟動時自動執行 | 若 `yhlib/cs3060701` 不存在則自動 `docker pull` |
| 建立管理員帳號 | `app` 啟動時自動執行 | 預設 `admin` / `admin1234`（可於 `.env` 覆寫） |

> **首次啟動較慢**：需編譯映像檔並拉取判題映像檔（約 GB 級），請耐心等候。

#### 關於 JWT 金鑰

> ⚠️ **本小節的 openssl 指令僅供對照，請勿執行。** 金鑰已由 `keygen` 容器自動生成，
> 在本機執行只會於專案根目錄留下一組**用不到的私鑰檔案**（系統讀取的是資料卷內的金鑰）。
> 若已誤執行，請刪除根目錄的 `private.pem` 與 `public.pem`。

《期末專案說明》指定之金鑰生成指令如下（**對照用，不需執行**）：

```
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out private.pem
openssl pkey -in private.pem -pubout -out public.pem
```

本系統即以**這兩道指令原封不動**生成 EC P-256 金鑰對，只是改於容器內執行（見 `scripts/gen-keys.sh`），因此本機無須安裝 OpenSSL。金鑰存放於 `keys` 資料卷，`app` 以唯讀方式掛載於 `/app/keys`。

實際要做的只有「確認金鑰已生成」，即下方指令：

```powershell
# 確認金鑰已生成
docker compose logs keygen
# → gen-keys: generated EC P-256 key pair in /app/keys

# 檢視金鑰檔案
docker compose exec app ls -l /app/keys
```

金鑰已存在時 `keygen` 會保留不覆寫（重新生成會使既有 JWT 全數失效）。若確需重新生成：

```powershell
docker compose down
docker volume rm backend_final_keys
docker compose up -d
```

### 1.3 確認啟動成功

```powershell
docker compose ps                   # app 與 db 應為 running；keygen 應為 exited (0)
docker compose logs app | Select-String "listening"
```

若出現 `REGS server listening on :8080` 即表示成功。

> 此處的 `:8080` 是**容器內部**的監聽埠，固定不變；從主機連線時要用的是**對外發布**的埠號，
> 兩者未必相同，取得方式見下一節。

亦可確認五張資料表皆已建立：

```powershell
docker compose exec db psql -U regs -d regs -c "\dt"
```

應列出 `users / problems / testcases / submissions / submission_logs`。

### 1.4 設定 API 位址變數（**必要步驟**）

後續所有章節的範例一律以 `$base` 作為網址前綴，因此**執行任何測試指令前，必須先在同一個 PowerShell 視窗設定此變數**，否則網址會變成空字串而連線失敗。

容器內固定監聽 8080，但**對外發布的埠號不一定是 8080**——它由 `.env` 的 `APP_PORT` 決定，本機 8080 被其他程式佔用時就必須改用別的埠。因此請以下列指令**自動取得**實際埠號，不要手動猜：

```powershell
$base = "http://127.0.0.1:$((docker compose port app 8080).Split(':')[-1])"
$base
```

> 須於專案根目錄執行（`docker compose` 需讀取 `docker-compose.yml`）。

接著驗證設定正確——**應回傳題目清單的 JSON**（全新資料庫則為空陣列 `[]`）：

```powershell
Invoke-RestMethod -Uri "$base/api/problems"
```

> ⚠️ **若回傳的是 HTML 而非 JSON**，例如：
>
> ```
> Access Error: 404 -- Not Found
> Cannot open document for: /api/problems
> ```
>
> 代表你連到的是**別的網頁伺服器**，而不是 REGS。這通常發生在直接沿用文件範例中的 8080，
> 而該埠正被其他程式（如 `ApplicationWebServer`）佔用時。請改用上方自動偵測的 `$base`。
> REGS 的回應一律是 JSON；即使查詢失敗也會是 `{"error":"..."}` 形式，絕不會是 HTML。

> **網址務必加雙引號**：PowerShell 只在雙引號字串內展開變數。寫成 `-Uri "$base/api/problems"` 才正確，
> 單引號 `'$base/api/problems'` 會被當成字面文字。
>
> **變數只存在於當前視窗**：`$base`、`$adminToken`、`$aliceToken` 等皆為 PowerShell 工作階段變數。
> 若關閉視窗或另開新視窗，需重新執行本節與第 2.3 節以重建這些變數。
>
> **複製指令時請勿包含提示字元**：從終端機畫面複製時容易連 `PS D:\...>` 一起帶入。
> `PS` 是 `Get-Process` 的別名，會導致 `Get-Process : 找不到接受引數 ... 的位置參數` 這類錯誤。

> **請使用 `127.0.0.1` 而非 `localhost`**：`localhost` 在 Windows 會優先解析為 IPv6 的 `::1`。
> 部分機器上會有其他行程（例如 `dllhost.exe` COM surrogate）搶先綁定 Docker 所發布埠號的
> IPv6 位址，連線雖能建立卻立即中斷，症狀為 `Invoke-RestMethod` 報「基礎連接已關閉」或
> `curl` 回傳 000。改用 IPv4 的 `127.0.0.1` 即可繞過。以 `netstat -ano | Select-String ":<埠號>"`
> 可確認是否有非 Docker 行程綁在 `[::1]` 上。

> **常用維運指令**
>
> | 指令 | 用途 |
> |------|------|
> | `docker compose logs -f app` | 追蹤伺服器日誌 |
> | `docker compose restart app` | 重啟伺服器 |
> | `docker compose up -d --build app` | 改完程式碼後重新編譯並重啟 |
> | `docker compose exec app sh` | 進入容器（storage 位於 `/app/storage`） |
> | `docker compose down` | 停止服務，保留資料庫、金鑰與 storage |
> | `docker compose down -v` | 停止並清除所有資料卷（含資料庫與金鑰） |

## 二、帳號與角色設定（後續測試之基礎）

《期末專案說明》定義了 Guest / User / Admin 三種角色，後續各項驗證皆需以不同角色進行，故先於此備妥帳號並取得 token。

### 2.1 Admin 帳號（開機自動建立）

`app` 啟動時會自動建立一組固定的管理員帳號（冪等，重啟不會重複建立或覆寫）：

| 帳號 | 密碼 | 角色 |
|------|------|------|
| `admin` | `admin1234` | `admin` |

帳號密碼可於 `.env` 以 `SEED_ADMIN_USERNAME` / `SEED_ADMIN_PASSWORD` 覆寫；留白則停用自動建立。

### 2.2 註冊一般使用者（Guest → User）

`POST /api/users/register` 為 Guest 端點，經此建立之帳號 role 一律為 `user`：

```powershell
Invoke-RestMethod -Uri "$base/api/users/register" -Method Post -ContentType "application/json" -Body '{"username":"alice","password":"pass123"}'
```

> 若回傳 **409 Conflict**，代表 `alice` 已存在（帳號名稱為 UNIQUE），直接進行下一步登入即可。
>
> 亦請勿以 `register` 建立名為 `admin` 的帳號——該帳號已由系統自動建立，重複註冊必然得到 409。若需要第二個管理員，可手動升級：
> `docker compose exec db psql -U regs -d regs -c "UPDATE users SET role='admin' WHERE username='<帳號>';"`

### 2.3 登入並取得 token（存入變數）

```powershell
$admin = Invoke-RestMethod -Uri "$base/api/users/login" -Method Post -ContentType "application/json" -Body '{"username":"admin","password":"admin1234"}'
$adminToken = $admin.token

$alice = Invoke-RestMethod -Uri "$base/api/users/login" -Method Post -ContentType "application/json" -Body '{"username":"alice","password":"pass123"}'
$aliceToken = $alice.token

# 取得 alice 的實際 user_id（後續統計與提交查詢一律使用此變數，避免寫死編號對不上）
$aliceId = (Invoke-RestMethod -Uri "$base/api/users/me" -Headers @{ Authorization = "Bearer $aliceToken" }).id
"alice user_id = $aliceId"
```

> **為何不直接寫死 `2`**：帳號 `id` 由資料庫自增序列產生，即使 `register` 因帳號已存在而失敗（回 409），序列仍會往前跳；重跑註冊或資料庫未清乾淨時，alice 的 `user_id` 便可能不是 `2`。故一律以 `$aliceId` 承接實際值。

> **關於 `Invoke-RestMethod` 的錯誤處理**：`Invoke-RestMethod` 遇到 401、403 等非 2xx 回應時，會擲出紅色例外訊息，此為預期行為（代表權限確實受到攔阻）。若需檢視伺服器回傳之錯誤內容，可將指令包裹於 `try { ... } catch { $_.ErrorDetails.Message }`。

## 三、自動化編譯管道（配分合計 20 分）

本節驗證系統接收專案壓縮檔、於隔離容器內完成 CMake 配置與編譯、執行並比對結果，最終回傳狀態與分段日誌之完整流程。

> **判題前置條件**
> - 提交之 ZIP 解壓後根目錄須包含 `CMakeLists.txt`（對應《期末專案說明》「預處理」階段之檢查）。
> - 判題所用之 `yhlib/cs3060701` 映像檔由 `app` 於啟動時自動確認並拉取，無須手動 `docker pull`。
>   可以 `docker compose logs app | Select-String "judge image"` 確認；若出現 `WARNING: judge image ... unavailable` 則表示拉取失敗。

### 3.1 建立測試題目

判題須先有題目。系統支援兩種判題模式：I/O 比對（`io`）與 test-based（`test-based`，對應 `docs/判題模式.md`）。以下先以 I/O 模式建立題目；test-based 模式之完整流程詳見第 3.7 節。

以 **admin token** 建立題目。`testcases` 為一組 `{input, expected}` 陣列，請將測資之輸入與標準答案填入（JSON 內之換行以 `\n` 表示）：

```powershell
$problem = @'
{
  "title": "A + B",
  "description": "讀入兩個整數，輸出其和。",
  "time_limit": 20,
  "testcases": [
    { "input": "3 2\n",   "expected": "5\n" },
    { "input": "10 20\n", "expected": "30\n" }
  ]
}
'@

$resp = Invoke-RestMethod -Uri "$base/api/problems" -Method Put -Headers @{ Authorization = "Bearer $adminToken" } -ContentType "application/json" -Body $problem
$ioProblemId = $resp.id
"A + B 題目 problem_id = $ioProblemId, judge_mode = $($resp.judge_mode)"
```

回傳之 `id` 存入 `$ioProblemId`（新資料庫首次建立時為 `1`），供第 3.4 節的狀態測試與第五節查詢沿用；`judge_mode` 為 `io`。此題採用一道最小的「A + B」題目（讀入兩整數、輸出其和），與 `test-programs/` 內各狀態測試程式相對應。至於完整之判題管線（ZIP 上傳、解壓、CMake 編譯、逐案執行、日誌），統一於第 3.7 節以 test-based 模式實機走查一次，本節 3.2 至 3.5 僅說明各評分檢查點並指向該處，不重複示範。

> `time_limit` 設為 20 秒以容納容器啟動時間，避免正常程式誤判 TLE（見第 3.4 節時限說明）；容器啟動較快的機器可自行調低。

> 若測資組數眾多或內容較長，直接編輯上方 here-string（`@' ... '@`）即可。亦可於後續以同一 `PUT /api/problems` 帶入 `"id": 1` 更新該題並整批替換測資。

### 3.2 ZIP 上傳與解壓縮（配分 3 分）

**檢查點**：支援接收 `.zip` 格式之專案檔，並於掛載至容器前正確解壓縮，且檢查目錄結構是否完整（須含 `CMakeLists.txt`）。

此檢查點於第 3.7 節完整示範，本節不重複提交：3.7 步驟 2 由 admin 上傳題目包 ZIP、步驟 4 由 User 提交學生程式 ZIP，系統皆會接收 `.zip`、解壓縮，並檢查根目錄是否含 `CMakeLists.txt`。相關驗證行為：

- 上傳題目包時，若 ZIP 根目錄缺少 `CMakeLists.txt`，`PUT /api/problems` 於驗證階段即回 **400 Bad Request**（見 `internal/api/handler/problem_handler.go` 之 `zipHasCMakeLists`）。
- 提交之學生程式若解壓後找不到 `CMakeLists.txt`，判題時將判為 `SE`（初始化錯誤），可於 `configure_log` 檢視原因。

### 3.3 CMake 管線自動化（配分 5 分）

**檢查點**：自動執行 Configure（`cmake -G Ninja -B build`）與 Build（`cmake --build build`）流程，並自動擷取各階段 Exit Code。

於第 3.7 節提交後，以下列指令查詢完整判題結果（PowerShell 無 `GET` 指令，發 GET 請求一律用 `Invoke-RestMethod`；`$opId` 為提交後取得的 `operator_id`）：

```powershell
# 完整判題結果：status 與 configure/compile/output 三段 log 一次回傳
Invoke-RestMethod -Uri "$base/api/submissions/$opId" -Headers @{ Authorization = "Bearer $aliceToken" }
```

回傳物件即為該筆提交的判題結果，其中 `configure_log` 與 `compile_log` 兩欄分別對應 CMake 管線之兩個階段：

| 欄位 | 對應階段 |
|------|---------|
| `configure_log` | `cmake -G Ninja -B build` 配置階段之輸出 |
| `compile_log` | `cmake --build build` 編譯階段之輸出 |

系統依各階段之 Exit Code 決定後續判定：配置階段失敗判為 `SE`，編譯階段失敗判為 `CE`（詳見第 3.4 節）。

### 3.4 五種基本狀態判定（配分 5 分）

**檢查點**：依執行結果準確回傳 AC、WA、CE、RE（另含 SE、TLE），透過輸出比對決定 AC/WA，並以 Exit Code 非 0 判定 RE。

`GET /api/submissions/{operatorId}` 回傳之 `status` 欄位即為判題結論：

| 狀態 | 意義 | 觸發條件 |
|------|------|---------|
| `AC` | Accepted（通過） | 輸出與標準答案完全一致 |
| `WA` | Wrong Answer（答案錯誤） | 輸出與標準答案不符 |
| `CE` | Compilation Error（編譯錯誤） | `cmake --build` 階段失敗（語法錯誤等） |
| `RE` | Runtime Error（執行錯誤） | 程式以非零 Exit Code 結束 |
| `SE` | Setup Error（初始化錯誤） | `cmake` 配置階段失敗（CMake 腳本有誤） |
| `TLE` | Time Limit Exceeded（逾時） | 執行時間超過題目 `time_limit` |

**如何查看 `status`**：`status` 存於提交結果的 `status` 欄位，需透過 API 查詢（PowerShell 無 `GET` 指令，一律以 `Invoke-RestMethod` 發送 GET 請求）。判題完成後，可用下列任一方式查看（`$opId` 為第 3.7 節提交後取得的 `operator_id`；若單獨執行，請將 `$opId` 代換為你的 operator_id）：

```powershell
# 方式一：查單一提交，只取狀態欄位
$d = Invoke-RestMethod -Uri "$base/api/submissions/$opId" -Headers @{ Authorization = "Bearer $aliceToken" }
$d.status                      # 例如印出 AC

# 方式二：列出自己的所有提交及其狀態
$r = Invoke-WebRequest -UseBasicParsing -Uri "$base/api/submissions" -Headers @{ Authorization = "Bearer $aliceToken" }
$r.Content | ConvertFrom-Json | Format-Table operator_id, problem_id, status -AutoSize

# 方式三：查指定使用者的提交（Guest 亦可，免 token；$aliceId 為 2.3 節取得的 alice user_id）
$r = Invoke-WebRequest -UseBasicParsing -Uri "$base/api/users/$aliceId/submissions"
$r.Content | ConvertFrom-Json | Format-Table operator_id, status -AutoSize
```

> **列表為何用 `Invoke-WebRequest` + `ConvertFrom-Json`，而非直接 `Invoke-RestMethod`**：Windows PowerShell 的 `Invoke-RestMethod` 在處理 **JSON 陣列**回應時，接 `Select-Object` / `Format-Table` 顯示偶爾會出現「明明有資料卻整列空白」的假象。改以 `Invoke-WebRequest` 取原始內容 `.Content`、再明確 `ConvertFrom-Json` 解析後顯示最穩定。查**單一物件**（如方式一、單筆提交結果）用 `Invoke-RestMethod` 則無此問題。

> 剛提交完 `status` 會是 `pending` 或 `running`，背景判題完成後才轉為 `AC` 等最終狀態；若查到仍是 `running`，隔幾秒重跑上方查詢即可（test-based 每案各起一個容器，會更慢）。切勿把 `output_log` 內學生程式印出的 `SUCCESS!` 誤認為 `status`。

欲逐一驗證各狀態，可分別提交：正確解答（應得 `AC`）、輸出錯誤之程式（`WA`）、含語法錯誤之程式（`CE`）、以非零碼結束之程式（`RE`）等，觀察 `status` 是否符合預期。以第 3.7 節之 test-based 題目為例，提交 `solution/` 應得 `AC`，改提交缺少 `Complex.cpp` 之 `template/` 則因連結失敗而得 `CE`。

> **判為 TLE 但程式實無問題？** 時限係針對整個 `docker run` 計時，**包含容器啟動時間**。於容器啟動較慢之環境（部分 Windows Docker Desktop 主機啟動單一容器可達 10 秒以上），請將題目 `time_limit` 適度放寬（例如 20 至 40 秒），否則可能誤判為 TLE。test-based 題目每一測資各啟動一個容器，尤須放寬。

> **程式正確卻判為 WA？** 輸出比對會正規化行尾空白與結尾空行，但其餘內容仍須完全一致。請以 `output_log` 比對期望輸出與實際輸出。另須注意，判題以啟發式方式尋找可執行檔（擷取 `build/` 下第一個可執行檔），結構較複雜之專案可能須調整 `internal/judge/judge.go` 之 `runScript`。

**提交 I/O 題目的完整範例**：以第 3.1 節的 A + B 題目為例，示範 I/O 模式「打包 → 提交 → 查結果」一輪。I/O 提交的 ZIP **根目錄須含 `CMakeLists.txt` 與原始碼**（與 test-based 只交原始碼、建置檔由題目包提供不同）：

```powershell
# 1. 打包一份 I/O 提交（此處借用 test-programs\ac；根目錄為 CMakeLists.txt + main.cpp）
Compress-Archive -Path "test-programs\ac\*" -DestinationPath ".\my-io.zip" -Force

# 2. 以 alice（User）提交至 A + B 題目，立即取得 operator_id
$resp = curl.exe -s -X POST "$base/api/submissions" -H "Authorization: Bearer $aliceToken" -F "problem_id=$ioProblemId" -F "file=@.\my-io.zip" | ConvertFrom-Json
$opId = $resp.operator_id
"operator_id = $opId"

# 3. 稍候查結果（背景判題完成後才會是最終狀態）
Start-Sleep -Seconds 10
Invoke-RestMethod -Uri "$base/api/submissions/$opId" -Headers @{ Authorization = "Bearer $aliceToken" }

# 只看狀態
(Invoke-RestMethod -Uri "$base/api/submissions/$opId" -Headers @{ Authorization = "Bearer $aliceToken" }).status   # 此範例預期 AC
```

> 提交指令與 test-based **完全相同**（同為 `POST /api/submissions`，同樣的 multipart 上傳）；差別只在 ZIP 內容——I/O 需自帶 `CMakeLists.txt`，test-based 只放原始碼、建置檔由題目包提供（見第 3.7 節）。

**各狀態的現成測試程式**：`test-programs/` 已備妥對應上述每一種狀態的 I/O 提交（`ac` / `wa` / `ce` / `re` / `tle` / `se-badcmake` / `se-nocmake`，其中 `se-nocmake` 故意不含 `CMakeLists.txt`，用以模擬學生漏掉建置檔），無須每次手寫。打包後提交至第 3.1 節建立的 `$ioProblemId` 即可逐一驗證：

```powershell
# 一鍵把每個資料夾各打包成 test-programs\dist\<狀態>.zip
powershell -File test-programs\pack.ps1
```

完整的「打包 → 一次提交七種 → 比對『預期 vs 實得』」流程，詳見 `test-programs/README.md`。

### 3.5 多分段日誌查詢（配分 5 分）

**檢查點**：提供 API 分別查詢配置、編譯與執行日誌，並儲存為實體檔案。

除於單一提交結果中一併回傳三段日誌外，系統亦提供分段查詢端點 `GET /api/submissions/{operatorId}/logs/{phase}`（`phase` 可為 `configure`、`compile`、`output`），回傳純文字。此三段查詢於第 3.7 節步驟 4 實機示範。三段對應內容如下：

| 日誌欄位 / phase | 內容 |
|------|------|
| `configure_log` / `configure` | 配置階段（`cmake -G`）輸出 |
| `compile_log` / `compile` | 編譯階段（`cmake --build`）輸出 |
| `output_log` / `output` | 逐測資執行與比對輸出（判錯時於此除錯） |

> 三段日誌亦會落地為實體檔案 `/app/storage/logs/<operatorId>/{configure,compile,output}.log`（位於 `regs-storage` 資料卷內）；分段查詢 API 會優先讀取實體檔案，找不到時方回退至資料庫副本。
>
> 欲直接檢視實體檔案：
>
> ```powershell
> docker compose exec app ls /app/storage/logs/$opId
> docker compose exec app cat /app/storage/logs/$opId/compile.log
> # 或整包複製到主機檢視
> docker compose cp app:/app/storage ./storage-export
> ```

### 3.6 容器網段隔離（配分 2 分）

**檢查點**：編譯容器與執行容器須位於不同 Network，執行容器必須完全斷網，執行階段使用 `--network none` 以防止網路攻擊。

各階段所用之網路模式如下（實作見 `internal/judge/judge.go`，由 `DockerRunner.Run` 之 `networkMode` 參數指定）：

| 階段 | 指令 | Network | 資源限制 |
|------|------|---------|---------|
| 配置 | `cmake -G Ninja` | `bridge`（允許下載相依套件） | 無 |
| 編譯 | `cmake --build` | `bridge` | 無 |
| **執行** | 學生程式 / ctest 測資 | **`none`（完全斷網）** | `--memory` / `--cpus` / `--pids-limit` |

可直接驗證執行階段所用之參數確實斷網：

```powershell
# 以判題執行階段相同的 --network none 啟動容器，確認無法對外連線
docker run --rm --network none yhlib/cs3060701 sh -c "getent hosts github.com || echo '[確認] 無法解析外部網域，已完全斷網'"

# 對照組：configure/build 階段使用的 bridge 網路則可正常連線
docker run --rm --network bridge yhlib/cs3060701 sh -c "getent hosts github.com > /dev/null && echo '[對照] bridge 可正常連線'"
```

亦可於判題進行中即時觀察實際啟動之判題容器（容器名稱前綴為 `regs-judge-`）：

```powershell
docker ps --filter "name=regs-judge-" --format "{{.Names}}`t{{.Networks}}"
```

執行階段之容器其 `Networks` 欄位應顯示 `none`。實作細節另見 `docs/判題模式.md`。

### 3.7 test-based 判題模式（以 `test-framework/113final001` 為例）

除上述 I/O 比對模式外，系統亦支援助教期末考所用之 **test-based 判題**（對應 `docs/判題模式.md`）。`test-framework/113final001` 與 `113final003` 即為此類題目之範例，本節完整演示一遍。

首先須釐清兩種角色所上傳之 ZIP：

| ZIP | 上傳者 | 內容 | 使用之 API |
|-----|--------|------|-----------|
| **題目包** | 助教（admin） | `CMakeLists.txt` + `cmake/`（判題腳本）+ `spec/`（隱藏測資） | `PUT /api/problems`（multipart） |
| **學生提交** | 學生（user） | 學生自行撰寫之原始碼 `*.cpp` / `*.h`（置於 ZIP 根目錄） | `POST /api/submissions` |

判題時，系統以**題目包**之 CMake 專案為基礎，設定 `-D SOURCE_ROOT=<學生原始碼>`，編譯後以 `ctest` 逐案執行，每一測資各得 PASS / FAIL。

範例題目之資料夾結構（`test-framework/113final001/`）：

```
CMakeLists.txt      ┐
cmake/AddJudge.cmake├─ 題目包需要此三者
spec/case1.h ... 5.h┘
solution/           ← 參考正解（作為「應通過之學生提交」測試）
template/           ← 空白樣板（缺 Complex.cpp，用以測試 CE）
```

#### 步驟 1：打包題目包（僅置入所需三者，勿將 solution 正解一併打包）

```powershell
$src = ".\test-framework\113final001"
$pkg = ".\pkg-f001"
Remove-Item $pkg -Recurse -Force -ErrorAction SilentlyContinue
New-Item -ItemType Directory $pkg | Out-Null
Copy-Item "$src\CMakeLists.txt" $pkg\
Copy-Item "$src\cmake" $pkg\ -Recurse
Copy-Item "$src\spec"  $pkg\ -Recurse
Compress-Archive -Path "$pkg\*" -DestinationPath .\f001-pkg.zip -Force
```

#### 步驟 2：以 admin 上傳題目包

```powershell
curl.exe -s -X PUT "$base/api/problems" -H "Authorization: Bearer $adminToken" `
  -F "title=113final001 Complex" -F "time_limit=40" -F "file=@.\f001-pkg.zip" | ConvertFrom-Json
```

回傳之 `judge_mode` 將為 `test-based`，請記下 `id`（以下假設為 `2`）。

#### 步驟 3：打包一份「學生提交」（以 `solution/` 作為正解，預期 AC）

```powershell
Compress-Archive -Path ".\test-framework\113final001\solution\*" -DestinationPath .\f001-sol.zip -Force
```

> `solution/` 內含 `Complex.cpp` / `Complex.h` / `entrypoint.cpp` / `test.h` / `case.h`，直接置於 ZIP 根目錄即可（夾帶之 PDF 不影響判題）。欲模擬**應失敗**之提交，改打包 `template\*`（缺少 `Complex.cpp`，連結失敗將判為 `CE`）。

#### 步驟 4：提交並檢視結果

```powershell
$resp = curl.exe -s -X POST "$base/api/submissions" -H "Authorization: Bearer $aliceToken" -F "problem_id=2" -F "file=@.\f001-sol.zip" | ConvertFrom-Json
$opId = $resp.operator_id

# test-based 每一測資各啟動一個容器，較 I/O 題耗時甚多，須多加等待
Start-Sleep -Seconds 30

# 提交結果（status 與三段日誌一併回傳）
Invoke-RestMethod -Uri "$base/api/submissions/$opId" -Headers @{ Authorization = "Bearer $aliceToken" }

# 分段查詢三段日誌（對應第 3.5 節；phase = configure | compile | output）
Invoke-RestMethod -Uri "$base/api/submissions/$opId/logs/configure" -Headers @{ Authorization = "Bearer $aliceToken" }
Invoke-RestMethod -Uri "$base/api/submissions/$opId/logs/compile"   -Headers @{ Authorization = "Bearer $aliceToken" }
Invoke-RestMethod -Uri "$base/api/submissions/$opId/logs/output"    -Headers @{ Authorization = "Bearer $aliceToken" }
```

正解將得 **API 回傳之 `status = AC`**；`output_log` 結尾則顯示判題器附加之 `=== Summary: 5/5 cases passed ===`。若仍在執行則為 `running`，稍候再行查詢。

> **關於 `output_log` 中出現的 `SUCCESS!`**：test-based 題目採用 doctest 測試框架，學生程式執行時會由框架自行於標準輸出印出 `SUCCESS!`（全數通過）或 `FAILURE!`（有失敗），此段文字因而出現在 `output_log` 內，屬於**程式自身的輸出**。它與 API 的 `status` 欄位為**不同層級**：`status` 係由後端判題器判定並寫入資料庫（全部通過即為 `AC`，見 `internal/judge/judge.go` 與 `internal/model/model.go` 之 `StatusAC = "AC"`）。因此日誌內含 `SUCCESS!`、而 `status` 為 `AC`，兩者皆屬正常，並不衝突。

> **關於 `Compress-Archive` 與子目錄**：Windows PowerShell 之 `Compress-Archive` 會以反斜線作為 ZIP 路徑分隔符（不符 ZIP 規範）。系統之解壓程式已會自動正規化，故含 `cmake/`、`spec/` 等子目錄之題目包仍可正常判題；若改用其他工具打包，仍建議確認 ZIP 內為正斜線路徑。

> **執行時間提醒**：test-based 題目含 5 個測資，每一測資各啟動一個容器，加上 configure/build 共約 8 個容器。於容器啟動較慢之機器上，整題可能需 1 至 2 分鐘，`time_limit` 亦須一併放寬（見第 3.4 節時限說明）。

## 四、非同步任務隊列與併發控制（配分合計 10 分）

### 4.1 非同步任務隊列（配分 5 分）

**檢查點**：接收提交後立即回傳 `operatorId`，評測過程於背景執行，且可任意重新執行某一 Job。

- **非同步回應**：`POST /api/submissions` 會**立即**回傳 202 與 `operator_id`（不等待判題完成），評測結果於背景產生。此行為已於第 3.7 節提交時觀察到——提交後立即取得 `operator_id`，須稍候再查詢方得結果。
- **重新執行 Job**：`POST /api/submissions/{operatorId}/rejudge` 會將該筆提交重設為 `pending` 並重新排入佇列（本人或 admin 可執行；改題後將載入最新題目定義）：

```powershell
Invoke-RestMethod -Uri "$base/api/submissions/$opId/rejudge" -Method Post -Headers @{ Authorization = "Bearer $aliceToken" }
```

### 4.2 併發控制機制（配分 5 分）

**檢查點**：限制同時進行評測之容器數量，超額任務須排隊（Pending），以 Semaphore 控制最大併發數。

同時進行評測之容器數受 `MAX_CONCURRENT_JOBS`（`.env`，預設 3）限制，超額之提交將排隊停於 `pending`。欲觀察排隊效果，連續送出數筆提交（沿用第 3.7 節的題目包題目與 `f001-sol.zip`）後立即查詢列表：

```powershell
# 連續送出 5 筆（同一 zip、同一題）
1..5 | ForEach-Object {
  curl.exe -s -X POST "$base/api/submissions" -H "Authorization: Bearer $aliceToken" -F "problem_id=2" -F "file=@.\f001-sol.zip" | Out-Null
}
# 立即查詢列表：預設 MAX_CONCURRENT_JOBS=3，可見部分為 running、其餘仍為 pending
$r = Invoke-WebRequest -UseBasicParsing -Uri "$base/api/submissions" -Headers @{ Authorization = "Bearer $aliceToken" }
$r.Content | ConvertFrom-Json | Format-Table operator_id, status -AutoSize
```

> test-based 提交每案各起一個容器，執行較慢，`pending` 排隊狀態會停留更久，反而更易觀察。

> 欲使排隊效果更為明顯，可將 `.env` 之 `MAX_CONCURRENT_JOBS` 設為 `1` 後重啟伺服器，再連續送出多筆提交。

### 5.2 RBAC 權限邊界驗證

依《期末專案說明》，權限大小為 Admin > User > Guest：標注為 Guest 之端點三種角色皆可存取；標注為 User 之端點 Admin 與 User 可存取；User 與 Admin 之請求皆須附上 `Authorization` Header。

```powershell
# 個人資料（User，須帶 token）
Invoke-RestMethod -Uri "$base/api/users/me" -Headers @{ Authorization = "Bearer $aliceToken" }

# 題目列表（Guest 可存取，無須 token）
Invoke-RestMethod -Uri "$base/api/problems"

# 登出（User）：伺服器會將該 token 的 jti 加入撤銷清單，令其立即失效
Invoke-RestMethod -Uri "$base/api/users/logout" -Method Post -Headers @{ Authorization = "Bearer $aliceToken" }
```

> **登出為真正失效，而非僅由客戶端丟棄 token**：JWT 本身無狀態，故伺服器另以撤銷清單
> （`internal/api/middleware/denylist.go`）記錄已登出 token 的 `jti`，`Auth` middleware 會一併檢查。
> 清單項目於該 token 原到期時間後自動清除，不會無限增長。

驗證登出確實生效——以**同一個**已登出的 token 再次呼叫 User 端點，應得 **401 Unauthorized**：

```powershell
try {
  Invoke-RestMethod -Uri "$base/api/users/me" -Headers @{ Authorization = "Bearer $aliceToken" }
  "未預期：登出後 token 仍可使用"
} catch {
  "已登出的 token 被拒絕：$($_.Exception.Response.StatusCode.value__)"   # 預期 401
}

# 後續章節仍需 alice 的 token，請重新登入取得新的
$alice = Invoke-RestMethod -Uri "$base/api/users/login" -Method Post -ContentType "application/json" -Body '{"username":"alice","password":"pass123"}'
$aliceToken = $alice.token
```

驗證權限確實受到攔阻：

- 以 `$aliceToken`（User）呼叫 `PUT /api/problems`（Admin 端點），應得 **403 Forbidden**。
- 不帶 token 呼叫 `POST /api/submissions`（User 端點），應得 **401 Unauthorized**。

### 5.3 題目、提交與統計之查詢與管理

以下題目 `problem_id` 為 `1`（第 3.1 節建立的 I/O 題目），alice 之 `user_id` 則使用第 2.3 節取得的 `$aliceId` 變數。

```powershell
# 查詢單一題目之完整描述（Guest）
Invoke-RestMethod -Uri "$base/api/problems/1"

# 下載題目測資（Admin）；I/O 題目回傳 JSON 測資陣列，test-based 題目回傳題目包 ZIP
Invoke-RestMethod -Uri "$base/api/problems/1/testcases" -Headers @{ Authorization = "Bearer $adminToken" }
# test-based 題目欲存為檔案時，改用 curl.exe：
curl.exe -s -OJ "$base/api/problems/1/testcases" -H "Authorization: Bearer $adminToken"

# 個人提交列表（User，帶 token 僅顯示本人提交）
$r = Invoke-WebRequest -UseBasicParsing -Uri "$base/api/submissions" -Headers @{ Authorization = "Bearer $aliceToken" }
$r.Content | ConvertFrom-Json | Format-Table operator_id, problem_id, status -AutoSize

# 指定使用者之提交列表（Guest 可存取，無須 token）
$r = Invoke-WebRequest -UseBasicParsing -Uri "$base/api/users/$aliceId/submissions"
$r.Content | ConvertFrom-Json | Format-Table operator_id, status -AutoSize

# 下載提交之原始 zip（本人或 admin）
curl.exe -s -OJ "$base/api/submissions/$opId/source" -H "Authorization: Bearer $aliceToken"

# 題目統計 / 使用者統計（Guest 可存取）
Invoke-RestMethod -Uri "$base/api/stats/problems/1"
Invoke-RestMethod -Uri "$base/api/stats/users/$aliceId"

# 刪除題目（Admin）；連帶刪除其測資，成功回傳 204 無內容
curl.exe -s -o NUL -w "%{http_code}`n" -X DELETE "$base/api/problems/1" -H "Authorization: Bearer $adminToken"
```

> 刪除題目後，再 `GET /api/problems/1` 將得 **404**。DELETE 改用 `curl.exe` 之原因為：`Invoke-RestMethod` 對 204（無回應內容）無內容可顯示，以 curl 檢視狀態碼較為直觀。
>
> **注意**：DELETE 為破壞性操作。若後續仍須以該題進行提交測試，請勿刪除將使用之題目——建議另建一臨時題目專供 DELETE 測試。

## 附錄：常見問題排解

**問：`docker` 指令報 `open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified`。**
答：Docker Desktop 引擎未啟動。請啟動 Docker Desktop，待鯨魚圖示轉為 running，並確認 `docker version` 能顯示 Server 區段。

**問：資料表沒建立 / 改了 `schema.sql` 後要如何套用？**
答：`app` 每次啟動都會自動套用內嵌的 `schema.sql`（語句皆為冪等），因此改完後執行 `docker compose up -d --build app` 即可，不需要 psql，也不必再 `down -v` 清空資料卷。

**問：`curl` 行為異常 / 不認得參數。**
答：PowerShell 之 `curl` 為 `Invoke-WebRequest` 之別名，並非真正的 curl。欲使用真正的 curl，請輸入完整名稱 `curl.exe`。

**問：API 回傳 HTML 的 `Access Error: 404 -- Not Found / Cannot open document for: /api/...`。**
答：連到的不是 REGS，而是**佔用該埠的其他網頁伺服器**。REGS 的回應一律為 JSON，錯誤時亦為 `{"error":"..."}`，絕不會是 HTML。原因多半是照抄文件範例的 8080，但本機 8080 已被別的程式（如 `ApplicationWebServer`）佔用。請依第 1.4 節以 `docker compose port app 8080` 取得實際對外埠號後重設 `$base`。

**問：容器明明在跑，`http://localhost:<埠號>` 卻連不上（連線被關閉 / curl 回 000）。**
答：改用 `http://127.0.0.1:<埠號>`。詳見第 1.4 節之說明——`localhost` 會優先走 IPv6，而該位址可能被其他行程搶先綁定。

**問：`docker compose up` 報 port is already allocated。**
答：對外埠號被佔用。於 `.env` 設定 `APP_PORT`（API）或 `DB_PORT`（Postgres）為其他值後重新 `docker compose up -d`。API 位址亦須同步調整（見第 1.4 節）。

**問：找不到 `make` 指令。**
答：Windows 預設未安裝 `make`。Makefile 僅為捷徑，其內容皆為 `docker compose ...` 指令，直接手動執行即可。

**問：`openssl` 無法辨識 / 找不到。**
答：不再需要本機 OpenSSL。金鑰由 `keygen` 一次性容器以容器內的 OpenSSL 生成，存放於 `keys` 資料卷。欲檢視：`docker compose run --rm keygen`（已存在則保留）；欲強制重新生成，先 `docker volume rm backend_final_keys` 再 `docker compose up -d`。

> **注意**：重新生成金鑰後，先前簽發之 JWT 將全數失效，需重新登入以取得新 token。

**問：test-based 題目上傳後判為 `SE`，configure log 顯示找不到 `AddJudge`。**
答：題目包 ZIP 缺少 `cmake/AddJudge.cmake`，或子目錄未一併打包。請依第 3.7 節步驟 1 之方式打包（以 `-Recurse` 將 `cmake/`、`spec/` 複製至暫存夾再壓縮），確保 ZIP 內含 `cmake/AddJudge.cmake`。

**問：提交後 status 持續為 `pending` / `running`。**
答：判題於背景執行，請以 `docker compose logs -f app` 檢視伺服器日誌。`app` 啟動時會自動確保 `yhlib/cs3060701` 存在，若當時拉取失敗，日誌會有 `WARNING: judge image ... unavailable`。

**問：程式正確卻判為 `WA`。**
答：輸出比對會正規化行尾空白與結尾空行，但其餘內容仍須完全一致。請以 `output_log` 比對期望輸出與實際輸出；另須注意判題以啟發式方式尋找可執行檔（擷取 `build/` 下第一個可執行檔），結構較複雜之專案可能須調整 `internal/judge/judge.go` 之 `runScript`。
