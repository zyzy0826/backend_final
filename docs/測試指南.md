# REGS 測試指南（Windows / PowerShell）

本文件說明如何在全新環境中啟動 REGS 系統，並依《期末專案說明》之評分基準，逐項驗證各功能是否正確運作。所有指令以 **Windows PowerShell** 為主。

本指南的驗證章節（第三至六節）刻意依《期末專案說明》評分表之四大分項編排，並於各小節標註對應配分，以利對照評分：

| 評分分項 | 配分 | 對應章節 |
|---------|:----:|---------|
| 自動化編譯管道 | 20 | 第三節 |
| 非同步任務隊列與併發控制 | 10 | 第四節 |
| 權限控管與查詢功能 | 20 | 第五節 |
| 文件 | 10 | 第六節 |

> **操作方式說明**：測試過程需同時使用**兩個 PowerShell 視窗**。
> - **視窗 A**：執行伺服器程序（`go run`，該程序會持續佔用此視窗並輸出日誌）。
> - **視窗 B**：執行各項測試指令。

## 一、測試環境準備（每台機器僅需執行一次）

### 1.1 前置需求

| 需求 | 說明 |
|------|------|
| Docker Desktop | 必須開啟並顯示 Engine running（工作列鯨魚圖示呈穩定狀態） |
| Go 1.25 以上 | 以 `go version` 確認（`go.mod` 要求 `go 1.25`） |
| JWT 金鑰 | 需具備 `keys/private.pem` 與 `keys/public.pem`（`keys/` 已列入 `.gitignore`，clone 後不會包含，須自行生成） |
| `.env` | 由 `.env.example` 複製而來，預設值於本機環境即可直接使用 |

### 1.2 生成 JWT 金鑰

由於 `keys/` 未納入版本控制，剛 clone 的專案必定缺少金鑰，此步驟為必要程序；若未執行，伺服器啟動時將因無法讀取金鑰而失敗。請先確認金鑰是否存在：

```powershell
Get-ChildItem keys      # 若已存在 private.pem 與 public.pem，可略過生成步驟
```

本系統伺服器預設由 `keys/` 讀取金鑰（參見 `.env` 之 `PRIVATE_KEY_PATH` 與 `PUBLIC_KEY_PATH`，以及 `docker-compose.yml` 所掛載之 `./keys`）。因此請於 `keys/` 資料夾內執行上述指令，使金鑰檔案落於 `keys/private.pem` 與 `keys/public.pem`。

**方式一：Git Bash**（`openssl` 本即位於 PATH，最貼近官方指令）

```bash
mkdir -p keys && cd keys
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out private.pem
openssl pkey -in private.pem -pubout -out public.pem
cd ..
```

**方式二：PowerShell**（預設無法辨識 `openssl`，須改用 Git 內建版本之完整路徑，並以 `Push-Location` 切換至金鑰資料夾後執行相同指令）

```powershell
$ossl = "C:\Program Files\Git\usr\bin\openssl.exe"   # Git 安裝路徑若不同，請自行調整
New-Item -ItemType Directory keys -Force | Out-Null
Push-Location keys
& $ossl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out private.pem
& $ossl pkey -in private.pem -pubout -out public.pem
Pop-Location
```

> **注意**：重新生成金鑰後，先前簽發之 JWT 將全數失效，需重新登入以取得新 token。

### 1.3 建立 .env

```powershell
Copy-Item .env.example .env
```

### 1.4 啟動資料庫

```powershell
docker compose down -v          # 清除舊資料卷，確保 schema 重新自動初始化
docker compose up db -d         # 啟動 Postgres

# 確認五張資料表皆已建立
docker compose exec db psql -U regs -d regs -c "\dt"
```

若列出 `users / problems / testcases / submissions / submission_logs` 即表示成功。

> **建表為自動程序**：`docker-compose.yml` 已將 `internal/db/schema.sql` 掛載至 Postgres 之 `/docker-entrypoint-initdb.d/`，資料卷首次初始化時會自動執行。此程序僅於資料卷為空時觸發，故上一步先以 `down -v` 清除。

### 1.5 啟動伺服器（視窗 A）

```powershell
go run ./cmd/server
```

若輸出 `REGS server listening on :8080` 即表示啟動成功。請保持此視窗開啟，伺服器日誌皆輸出於此。

> **各階段所需服務對照**
>
> | 測試項目 | Docker Desktop | db 容器 | 伺服器（go run） | judge image |
> |---|:---:|:---:|:---:|:---:|
> | 註冊 / 登入 / 題目 / 統計等 API | 是 | 是 | 是 | — |
> | 提交與判題 | 是 | 是 | 是 | 是（須預先 pull） |

## 二、帳號與角色設定（後續測試之基礎）

後續各項驗證皆需以不同角色之帳號進行，故先於此建立測試帳號並取得 token。

### 2.1 註冊兩個帳號

```powershell
Invoke-RestMethod -Uri http://localhost:8080/api/users/register -Method Post -ContentType "application/json" -Body '{"username":"admin","password":"pass123"}'
Invoke-RestMethod -Uri http://localhost:8080/api/users/register -Method Post -ContentType "application/json" -Body '{"username":"alice","password":"pass123"}'
```

### 2.2 將 admin 帳號升級為管理員

經 `register` 建立之帳號 role 一律為 `user`；欲測試 Admin 專屬端點，須手動升級：

```powershell
docker compose exec db psql -U regs -d regs -c "UPDATE users SET role='admin' WHERE username='admin';"
```

### 2.3 登入並取得 token（存入變數）

```powershell
$admin = Invoke-RestMethod -Uri http://localhost:8080/api/users/login -Method Post -ContentType "application/json" -Body '{"username":"admin","password":"pass123"}'
$adminToken = $admin.token

$alice = Invoke-RestMethod -Uri http://localhost:8080/api/users/login -Method Post -ContentType "application/json" -Body '{"username":"alice","password":"pass123"}'
$aliceToken = $alice.token

# 取得 alice 的實際 user_id（後續統計與提交查詢一律使用此變數，避免寫死編號對不上）
$aliceId = (Invoke-RestMethod -Uri http://localhost:8080/api/users/me -Headers @{ Authorization = "Bearer $aliceToken" }).id
"alice user_id = $aliceId"
```

> **為何不直接寫死 `2`**：帳號 `id` 由資料庫自增序列產生，即使 `register` 因帳號已存在而失敗（回 409），序列仍會往前跳；重跑註冊或資料庫未清乾淨時，alice 的 `user_id` 便可能不是 `2`。故一律以 `$aliceId` 承接實際值。

> **關於 `Invoke-RestMethod` 的錯誤處理**：`Invoke-RestMethod` 遇到 401、403 等非 2xx 回應時，會擲出紅色例外訊息，此為預期行為（代表權限確實受到攔阻）。若需檢視伺服器回傳之錯誤內容，可將指令包裹於 `try { ... } catch { $_.ErrorDetails.Message }`。

## 三、自動化編譯管道（配分合計 20 分）

本節驗證系統接收專案壓縮檔、於隔離容器內完成 CMake 配置與編譯、執行並比對結果，最終回傳狀態與分段日誌之完整流程。

> **判題前置條件**
> - 提交之 ZIP 解壓後根目錄須包含 `CMakeLists.txt`。
> - 判題會呼叫 Docker 執行 `yhlib/cs3060701` 映像檔，請先行拉取：`docker pull yhlib/cs3060701`。

### 3.1 建立測試題目

判題須先有題目。系統支援兩種判題模式：I/O 比對（`io`）與 test-based（`test-based`，對應 `docs/判題模式.md`）。以下先以 I/O 模式建立題目；test-based 模式之完整流程詳見第 3.7 節。

以 **admin token** 建立題目。`testcases` 為一組 `{input, expected}` 陣列，請將測資之輸入與標準答案填入（JSON 內之換行以 `\n` 表示）：

```powershell
$problem = @'
{
  "title": "A + B",
  "description": "讀入兩個整數，輸出其和。",
  "time_limit": 20,
  "testcases": [
    { "input": "3 2\n",   "expected": "5\n" },
    { "input": "10 20\n", "expected": "30\n" }
  ]
}
'@

$resp = Invoke-RestMethod -Uri http://localhost:8080/api/problems -Method Put -Headers @{ Authorization = "Bearer $adminToken" } -ContentType "application/json" -Body $problem
$ioProblemId = $resp.id
"A + B 題目 problem_id = $ioProblemId, judge_mode = $($resp.judge_mode)"
```

回傳之 `id` 存入 `$ioProblemId`（新資料庫首次建立時為 `1`），供第 3.4 節的狀態測試與第五節查詢沿用；`judge_mode` 為 `io`。此題採用一道最小的「A + B」題目（讀入兩整數、輸出其和），與 `test-programs/` 內各狀態測試程式相對應。至於完整之判題管線（ZIP 上傳、解壓、CMake 編譯、逐案執行、日誌），統一於第 3.7 節以 test-based 模式實機走查一次，本節 3.2 至 3.5 僅說明各評分檢查點並指向該處，不重複示範。

> `time_limit` 設為 20 秒以容納容器啟動時間，避免正常程式誤判 TLE（見第 3.4 節時限說明）；容器啟動較快的機器可自行調低。

> 若測資組數眾多或內容較長，直接編輯上方 here-string（`@' ... '@`）即可。亦可於後續以同一 `PUT /api/problems` 帶入 `"id": 1` 更新該題並整批替換測資。

### 3.2 ZIP 上傳與解壓縮（配分 3 分）

**檢查點**：支援接收 `.zip` 格式之專案檔，並於掛載至容器前正確解壓縮，且檢查目錄結構是否完整（須含 `CMakeLists.txt`）。

此檢查點於第 3.7 節完整示範，本節不重複提交：3.7 步驟 2 由 admin 上傳題目包 ZIP、步驟 4 由 User 提交學生程式 ZIP，系統皆會接收 `.zip`、解壓縮，並檢查根目錄是否含 `CMakeLists.txt`。相關驗證行為：

- 上傳題目包時，若 ZIP 根目錄缺少 `CMakeLists.txt`，`PUT /api/problems` 於驗證階段即回 **400 Bad Request**（見 `internal/api/handler/problem_handler.go` 之 `zipHasCMakeLists`）。
- 提交之學生程式若解壓後找不到 `CMakeLists.txt`，判題時將判為 `SE`（初始化錯誤），可於 `configure_log` 檢視原因。

### 3.3 CMake 管線自動化（配分 5 分）

**檢查點**：自動執行 Configure（`cmake -G Ninja -B build`）與 Build（`cmake --build build`）流程，並自動擷取各階段 Exit Code。

於第 3.7 節提交後，以下列指令查詢完整判題結果（PowerShell 無 `GET` 指令，發 GET 請求一律用 `Invoke-RestMethod`；`$opId` 為提交後取得的 `operator_id`）：

```powershell
# 完整判題結果：status 與 configure/compile/output 三段 log 一次回傳
Invoke-RestMethod -Uri "http://localhost:8080/api/submissions/$opId" -Headers @{ Authorization = "Bearer $aliceToken" }
```

回傳物件即為該筆提交的判題結果，其中 `configure_log` 與 `compile_log` 兩欄分別對應 CMake 管線之兩個階段：

| 欄位 | 對應階段 |
|------|---------|
| `configure_log` | `cmake -G Ninja -B build` 配置階段之輸出 |
| `compile_log` | `cmake --build build` 編譯階段之輸出 |

系統依各階段之 Exit Code 決定後續判定：配置階段失敗判為 `SE`，編譯階段失敗判為 `CE`（詳見第 3.4 節）。

### 3.4 五種基本狀態判定（配分 5 分）

**檢查點**：依執行結果準確回傳 AC、WA、CE、RE（另含 SE、TLE），透過輸出比對決定 AC/WA，並以 Exit Code 非 0 判定 RE。

`GET /api/submissions/{operatorId}` 回傳之 `status` 欄位即為判題結論：

| 狀態 | 意義 | 觸發條件 |
|------|------|---------|
| `AC` | Accepted（通過） | 輸出與標準答案完全一致 |
| `WA` | Wrong Answer（答案錯誤） | 輸出與標準答案不符 |
| `CE` | Compilation Error（編譯錯誤） | `cmake --build` 階段失敗（語法錯誤等） |
| `RE` | Runtime Error（執行錯誤） | 程式以非零 Exit Code 結束 |
| `SE` | Setup Error（初始化錯誤） | `cmake` 配置階段失敗（CMake 腳本有誤） |
| `TLE` | Time Limit Exceeded（逾時） | 執行時間超過題目 `time_limit` |

**如何查看 `status`**：`status` 存於提交結果的 `status` 欄位，需透過 API 查詢（PowerShell 無 `GET` 指令，一律以 `Invoke-RestMethod` 發送 GET 請求）。判題完成後，可用下列任一方式查看（`$opId` 為第 3.7 節提交後取得的 `operator_id`；若單獨執行，請將 `$opId` 代換為你的 operator_id）：

```powershell
# 方式一：查單一提交，只取狀態欄位
$d = Invoke-RestMethod -Uri "http://localhost:8080/api/submissions/$opId" -Headers @{ Authorization = "Bearer $aliceToken" }
$d.status                      # 例如印出 AC

# 方式二：列出自己的所有提交及其狀態
$r = Invoke-WebRequest -Uri http://localhost:8080/api/submissions -Headers @{ Authorization = "Bearer $aliceToken" }
$r.Content | ConvertFrom-Json | Format-Table operator_id, problem_id, status -AutoSize

# 方式三：查指定使用者的提交（Guest 亦可，免 token；$aliceId 為 2.3 節取得的 alice user_id）
$r = Invoke-WebRequest -Uri "http://localhost:8080/api/users/$aliceId/submissions"
$r.Content | ConvertFrom-Json | Format-Table operator_id, status -AutoSize
```

> **列表為何用 `Invoke-WebRequest` + `ConvertFrom-Json`，而非直接 `Invoke-RestMethod`**：Windows PowerShell 的 `Invoke-RestMethod` 在處理 **JSON 陣列**回應時，接 `Select-Object` / `Format-Table` 顯示偶爾會出現「明明有資料卻整列空白」的假象。改以 `Invoke-WebRequest` 取原始內容 `.Content`、再明確 `ConvertFrom-Json` 解析後顯示最穩定。查**單一物件**（如方式一、單筆提交結果）用 `Invoke-RestMethod` 則無此問題。

> 剛提交完 `status` 會是 `pending` 或 `running`，背景判題完成後才轉為 `AC` 等最終狀態；若查到仍是 `running`，隔幾秒重跑上方查詢即可（test-based 每案各起一個容器，會更慢）。切勿把 `output_log` 內學生程式印出的 `SUCCESS!` 誤認為 `status`。

欲逐一驗證各狀態，可分別提交：正確解答（應得 `AC`）、輸出錯誤之程式（`WA`）、含語法錯誤之程式（`CE`）、以非零碼結束之程式（`RE`）等，觀察 `status` 是否符合預期。以第 3.7 節之 test-based 題目為例，提交 `solution/` 應得 `AC`，改提交缺少 `Complex.cpp` 之 `template/` 則因連結失敗而得 `CE`。

> **判為 TLE 但程式實無問題？** 時限係針對整個 `docker run` 計時，**包含容器啟動時間**。於容器啟動較慢之環境（部分 Windows Docker Desktop 主機啟動單一容器可達 10 秒以上），請將題目 `time_limit` 適度放寬（例如 20 至 40 秒），否則可能誤判為 TLE。test-based 題目每一測資各啟動一個容器，尤須放寬。

> **程式正確卻判為 WA？** 輸出比對會正規化行尾空白與結尾空行，但其餘內容仍須完全一致。請以 `output_log` 比對期望輸出與實際輸出。另須注意，判題以啟發式方式尋找可執行檔（擷取 `build/` 下第一個可執行檔），結構較複雜之專案可能須調整 `internal/judge/judge.go` 之 `runScript`。

**提交 I/O 題目的完整範例**：以第 3.1 節的 A + B 題目為例，示範 I/O 模式「打包 → 提交 → 查結果」一輪。I/O 提交的 ZIP **根目錄須含 `CMakeLists.txt` 與原始碼**（與 test-based 只交原始碼、建置檔由題目包提供不同）：

```powershell
# 1. 打包一份 I/O 提交（此處借用 test-programs\ac；根目錄為 CMakeLists.txt + main.cpp）
Compress-Archive -Path "test-programs\ac\*" -DestinationPath ".\my-io.zip" -Force

# 2. 以 alice（User）提交至 A + B 題目，立即取得 operator_id
$resp = curl.exe -s -X POST http://localhost:8080/api/submissions -H "Authorization: Bearer $aliceToken" -F "problem_id=$ioProblemId" -F "file=@.\my-io.zip" | ConvertFrom-Json
$opId = $resp.operator_id
"operator_id = $opId"

# 3. 稍候查結果（背景判題完成後才會是最終狀態）
Start-Sleep -Seconds 10
Invoke-RestMethod -Uri "http://localhost:8080/api/submissions/$opId" -Headers @{ Authorization = "Bearer $aliceToken" }

# 只看狀態
(Invoke-RestMethod -Uri "http://localhost:8080/api/submissions/$opId" -Headers @{ Authorization = "Bearer $aliceToken" }).status   # 此範例預期 AC
```

> 提交指令與 test-based **完全相同**（同為 `POST /api/submissions`，同樣的 multipart 上傳）；差別只在 ZIP 內容——I/O 需自帶 `CMakeLists.txt`，test-based 只放原始碼、建置檔由題目包提供（見第 3.7 節）。

**各狀態的現成測試程式**：`test-programs/` 已備妥對應上述每一種狀態的 I/O 提交（`ac` / `wa` / `ce` / `re` / `tle` / `se-badcmake` / `se-nocmake`，其中 `se-nocmake` 故意不含 `CMakeLists.txt`，用以模擬學生漏掉建置檔），無須每次手寫。打包後提交至第 3.1 節建立的 `$ioProblemId` 即可逐一驗證：

```powershell
# 一鍵把每個資料夾各打包成 test-programs\dist\<狀態>.zip
powershell -File test-programs\pack.ps1
```

完整的「打包 → 一次提交七種 → 比對『預期 vs 實得』」流程，詳見 `test-programs/README.md`。

### 3.5 多分段日誌查詢（配分 5 分）

**檢查點**：提供 API 分別查詢配置、編譯與執行日誌，並儲存為實體檔案。

除於單一提交結果中一併回傳三段日誌外，系統亦提供分段查詢端點 `GET /api/submissions/{operatorId}/logs/{phase}`（`phase` 可為 `configure`、`compile`、`output`），回傳純文字。此三段查詢於第 3.7 節步驟 4 實機示範。三段對應內容如下：

| 日誌欄位 / phase | 內容 |
|------|------|
| `configure_log` / `configure` | 配置階段（`cmake -G`）輸出 |
| `compile_log` / `compile` | 編譯階段（`cmake --build`）輸出 |
| `output_log` / `output` | 逐測資執行與比對輸出（判錯時於此除錯） |

> 三段日誌亦會落地為實體檔案 `storage/logs/<operatorId>/{configure,compile,output}.log`；分段查詢 API 會優先讀取實體檔案，找不到時方回退至資料庫副本。

### 3.6 容器網段隔離（配分 2 分）

**檢查點**：編譯容器與執行容器須位於不同 Network，執行容器必須完全斷網，執行階段使用 `--network none` 以防止網路攻擊。

此項為架構層級之保證，無法直接透過 API 觀察：configure/build 階段使用 bridge 網路，執行階段則以 `--network none` 完全斷網。實作細節參見 `docs/判題模式.md` 及 `internal/judge`。

### 3.7 test-based 判題模式（以 `test-framework/113final001` 為例）

除上述 I/O 比對模式外，系統亦支援助教期末考所用之 **test-based 判題**（對應 `docs/判題模式.md`）。`test-framework/113final001` 與 `113final003` 即為此類題目之範例，本節完整演示一遍。

首先須釐清兩種角色所上傳之 ZIP：

| ZIP | 上傳者 | 內容 | 使用之 API |
|-----|--------|------|-----------|
| **題目包** | 助教（admin） | `CMakeLists.txt` + `cmake/`（判題腳本）+ `spec/`（隱藏測資） | `PUT /api/problems`（multipart） |
| **學生提交** | 學生（user） | 學生自行撰寫之原始碼 `*.cpp` / `*.h`（置於 ZIP 根目錄） | `POST /api/submissions` |

判題時，系統以**題目包**之 CMake 專案為基礎，設定 `-D SOURCE_ROOT=<學生原始碼>`，編譯後以 `ctest` 逐案執行，每一測資各得 PASS / FAIL。

範例題目之資料夾結構（`test-framework/113final001/`）：

```
CMakeLists.txt      ┐
cmake/AddJudge.cmake├─ 題目包需要此三者
spec/case1.h ... 5.h┘
solution/           ← 參考正解（作為「應通過之學生提交」測試）
template/           ← 空白樣板（缺 Complex.cpp，用以測試 CE）
```

#### 步驟 1：打包題目包（僅置入所需三者，勿將 solution 正解一併打包）

```powershell
$src = ".\test-framework\113final001"
$pkg = ".\pkg-f001"
Remove-Item $pkg -Recurse -Force -ErrorAction SilentlyContinue
New-Item -ItemType Directory $pkg | Out-Null
Copy-Item "$src\CMakeLists.txt" $pkg\
Copy-Item "$src\cmake" $pkg\ -Recurse
Copy-Item "$src\spec"  $pkg\ -Recurse
Compress-Archive -Path "$pkg\*" -DestinationPath .\f001-pkg.zip -Force
```

#### 步驟 2：以 admin 上傳題目包

```powershell
curl.exe -s -X PUT http://localhost:8080/api/problems -H "Authorization: Bearer $adminToken" `
  -F "title=113final001 Complex" -F "time_limit=40" -F "file=@.\f001-pkg.zip" | ConvertFrom-Json
```

回傳之 `judge_mode` 將為 `test-based`，請記下 `id`（以下假設為 `2`）。

#### 步驟 3：打包一份「學生提交」（以 `solution/` 作為正解，預期 AC）

```powershell
Compress-Archive -Path ".\test-framework\113final001\solution\*" -DestinationPath .\f001-sol.zip -Force
```

> `solution/` 內含 `Complex.cpp` / `Complex.h` / `entrypoint.cpp` / `test.h` / `case.h`，直接置於 ZIP 根目錄即可（夾帶之 PDF 不影響判題）。欲模擬**應失敗**之提交，改打包 `template\*`（缺少 `Complex.cpp`，連結失敗將判為 `CE`）。

#### 步驟 4：提交並檢視結果

```powershell
$resp = curl.exe -s -X POST http://localhost:8080/api/submissions -H "Authorization: Bearer $aliceToken" -F "problem_id=2" -F "file=@.\f001-sol.zip" | ConvertFrom-Json
$opId = $resp.operator_id

# test-based 每一測資各啟動一個容器，較 I/O 題耗時甚多，須多加等待
Start-Sleep -Seconds 30

# 提交結果（status 與三段日誌一併回傳）
Invoke-RestMethod -Uri "http://localhost:8080/api/submissions/$opId" -Headers @{ Authorization = "Bearer $aliceToken" }

# 分段查詢三段日誌（對應第 3.5 節；phase = configure | compile | output）
Invoke-RestMethod -Uri "http://localhost:8080/api/submissions/$opId/logs/configure" -Headers @{ Authorization = "Bearer $aliceToken" }
Invoke-RestMethod -Uri "http://localhost:8080/api/submissions/$opId/logs/compile"   -Headers @{ Authorization = "Bearer $aliceToken" }
Invoke-RestMethod -Uri "http://localhost:8080/api/submissions/$opId/logs/output"    -Headers @{ Authorization = "Bearer $aliceToken" }
```

正解將得 **API 回傳之 `status = AC`**；`output_log` 結尾則顯示判題器附加之 `=== Summary: 5/5 cases passed ===`。若仍在執行則為 `running`，稍候再行查詢。

> **關於 `output_log` 中出現的 `SUCCESS!`**：test-based 題目採用 doctest 測試框架，學生程式執行時會由框架自行於標準輸出印出 `SUCCESS!`（全數通過）或 `FAILURE!`（有失敗），此段文字因而出現在 `output_log` 內，屬於**程式自身的輸出**。它與 API 的 `status` 欄位為**不同層級**：`status` 係由後端判題器判定並寫入資料庫（全部通過即為 `AC`，見 `internal/judge/judge.go` 與 `internal/model/model.go` 之 `StatusAC = "AC"`）。因此日誌內含 `SUCCESS!`、而 `status` 為 `AC`，兩者皆屬正常，並不衝突。

> **關於 `Compress-Archive` 與子目錄**：Windows PowerShell 之 `Compress-Archive` 會以反斜線作為 ZIP 路徑分隔符（不符 ZIP 規範）。系統之解壓程式已會自動正規化，故含 `cmake/`、`spec/` 等子目錄之題目包仍可正常判題；若改用其他工具打包，仍建議確認 ZIP 內為正斜線路徑。

> **執行時間提醒**：test-based 題目含 5 個測資，每一測資各啟動一個容器，加上 configure/build 共約 8 個容器。於容器啟動較慢之機器上，整題可能需 1 至 2 分鐘，`time_limit` 亦須一併放寬（見第 3.4 節時限說明）。

## 四、非同步任務隊列與併發控制（配分合計 10 分）

### 4.1 非同步任務隊列（配分 5 分）

**檢查點**：接收提交後立即回傳 `operatorId`，評測過程於背景執行，且可任意重新執行某一 Job。

- **非同步回應**：`POST /api/submissions` 會**立即**回傳 202 與 `operator_id`（不等待判題完成），評測結果於背景產生。此行為已於第 3.7 節提交時觀察到——提交後立即取得 `operator_id`，須稍候再查詢方得結果。
- **重新執行 Job**：`POST /api/submissions/{operatorId}/rejudge` 會將該筆提交重設為 `pending` 並重新排入佇列（本人或 admin 可執行；改題後將載入最新題目定義）：

```powershell
Invoke-RestMethod -Uri "http://localhost:8080/api/submissions/$opId/rejudge" -Method Post -Headers @{ Authorization = "Bearer $aliceToken" }
```

### 4.2 併發控制機制（配分 5 分）

**檢查點**：限制同時進行評測之容器數量，超額任務須排隊（Pending），以 Semaphore 控制最大併發數。

同時進行評測之容器數受 `MAX_CONCURRENT_JOBS`（`.env`，預設 3）限制，超額之提交將排隊停於 `pending`。欲觀察排隊效果，連續送出數筆提交（沿用第 3.7 節的題目包題目與 `f001-sol.zip`）後立即查詢列表：

```powershell
# 連續送出 5 筆（同一 zip、同一題）
1..5 | ForEach-Object {
  curl.exe -s -X POST http://localhost:8080/api/submissions -H "Authorization: Bearer $aliceToken" -F "problem_id=2" -F "file=@.\f001-sol.zip" | Out-Null
}
# 立即查詢列表：預設 MAX_CONCURRENT_JOBS=3，可見部分為 running、其餘仍為 pending
$r = Invoke-WebRequest -Uri http://localhost:8080/api/submissions -Headers @{ Authorization = "Bearer $aliceToken" }
$r.Content | ConvertFrom-Json | Format-Table operator_id, status -AutoSize
```

> test-based 提交每案各起一個容器，執行較慢，`pending` 排隊狀態會停留更久，反而更易觀察。

> 欲使排隊效果更為明顯，可將 `.env` 之 `MAX_CONCURRENT_JOBS` 設為 `1` 後重啟伺服器，再連續送出多筆提交。

### 5.2 RBAC 權限邊界驗證

依《期末專案說明》，權限大小為 Admin > User > Guest：標注為 Guest 之端點三種角色皆可存取；標注為 User 之端點 Admin 與 User 可存取；User 與 Admin 之請求皆須附上 `Authorization` Header。

```powershell
# 個人資料（User，須帶 token）
Invoke-RestMethod -Uri http://localhost:8080/api/users/me -Headers @{ Authorization = "Bearer $aliceToken" }

# 題目列表（Guest 可存取，無須 token）
Invoke-RestMethod -Uri http://localhost:8080/api/problems

# 登出（User）：JWT 為無狀態，伺服器僅回傳訊息，客戶端自行丟棄 token 即可
Invoke-RestMethod -Uri http://localhost:8080/api/users/logout -Method Post -Headers @{ Authorization = "Bearer $aliceToken" }
```

驗證權限確實受到攔阻：

- 以 `$aliceToken`（User）呼叫 `PUT /api/problems`（Admin 端點），應得 **403 Forbidden**。
- 不帶 token 呼叫 `POST /api/submissions`（User 端點），應得 **401 Unauthorized**。

### 5.3 題目、提交與統計之查詢與管理

以下題目 `problem_id` 為 `1`（第 3.1 節建立的 I/O 題目），alice 之 `user_id` 則使用第 2.3 節取得的 `$aliceId` 變數。

```powershell
# 查詢單一題目之完整描述（Guest）
Invoke-RestMethod -Uri http://localhost:8080/api/problems/1

# 下載題目測資（Admin）；I/O 題目回傳 JSON 測資陣列，test-based 題目回傳題目包 ZIP
Invoke-RestMethod -Uri http://localhost:8080/api/problems/1/testcases -Headers @{ Authorization = "Bearer $adminToken" }
# test-based 題目欲存為檔案時，改用 curl.exe：
curl.exe -s -OJ http://localhost:8080/api/problems/1/testcases -H "Authorization: Bearer $adminToken"

# 個人提交列表（User，帶 token 僅顯示本人提交）
$r = Invoke-WebRequest -Uri http://localhost:8080/api/submissions -Headers @{ Authorization = "Bearer $aliceToken" }
$r.Content | ConvertFrom-Json | Format-Table operator_id, problem_id, status -AutoSize

# 指定使用者之提交列表（Guest 可存取，無須 token）
$r = Invoke-WebRequest -Uri "http://localhost:8080/api/users/$aliceId/submissions"
$r.Content | ConvertFrom-Json | Format-Table operator_id, status -AutoSize

# 下載提交之原始 zip（本人或 admin）
curl.exe -s -OJ http://localhost:8080/api/submissions/$opId/source -H "Authorization: Bearer $aliceToken"

# 題目統計 / 使用者統計（Guest 可存取）
Invoke-RestMethod -Uri http://localhost:8080/api/stats/problems/1
Invoke-RestMethod -Uri "http://localhost:8080/api/stats/users/$aliceId"

# 刪除題目（Admin）；連帶刪除其測資，成功回傳 204 無內容
curl.exe -s -o NUL -w "%{http_code}`n" -X DELETE http://localhost:8080/api/problems/1 -H "Authorization: Bearer $adminToken"
```

> 刪除題目後，再 `GET /api/problems/1` 將得 **404**。DELETE 改用 `curl.exe` 之原因為：`Invoke-RestMethod` 對 204（無回應內容）無內容可顯示，以 curl 檢視狀態碼較為直觀。
>
> **注意**：DELETE 為破壞性操作。若後續仍須以該題進行提交測試，請勿刪除將使用之題目——建議另建一臨時題目專供 DELETE 測試。

## 附錄：常見問題排解

**問：`docker` 指令報 `open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified`。**
答：Docker Desktop 引擎未啟動。請啟動 Docker Desktop，待鯨魚圖示轉為 running，並確認 `docker version` 能顯示 Server 區段。

**問：`... < internal/db/schema.sql` 於 PowerShell 無法運作。**
答：PowerShell 不支援 `<` 輸入重導向。請改用自動初始化（第 1.4 節），或執行 `docker compose cp internal/db/schema.sql db:/tmp/schema.sql; docker compose exec db psql -U regs -d regs -f /tmp/schema.sql`。

**問：`curl` 行為異常 / 不認得參數。**
答：PowerShell 之 `curl` 為 `Invoke-WebRequest` 之別名，並非真正的 curl。欲使用真正的 curl，請輸入完整名稱 `curl.exe`。

**問：伺服器啟動即報 `db: ... connection refused`。**
答：`go run` 於主機上執行，需 db 之 5432 port 對主機開放。`docker-compose.yml` 之 `db` 服務已加入 `ports: - "5432:5432"`；若本機 5432 已被其他 Postgres 佔用，請改為 `"5433:5432"` 並同步修改 `.env` 之 `DATABASE_URL`。

**問：找不到 `make` 指令。**
答：Windows 預設未安裝 `make`。Makefile 內之指令直接手動執行即可（金鑰見第 1.2 節、啟動見第 1.5 節）。

**問：`openssl` 無法辨識 / 找不到。**
答：Windows PowerShell 之 PATH 未包含 openssl。請先以 `Get-ChildItem keys` 確認金鑰是否已存在；若須生成，請使用 Git 內建 openssl 之完整路徑，或改用 Git Bash（見第 1.2 節）。

**問：test-based 題目上傳後判為 `SE`，configure log 顯示找不到 `AddJudge`。**
答：題目包 ZIP 缺少 `cmake/AddJudge.cmake`，或子目錄未一併打包。請依第 3.7 節步驟 1 之方式打包（以 `-Recurse` 將 `cmake/`、`spec/` 複製至暫存夾再壓縮），確保 ZIP 內含 `cmake/AddJudge.cmake`。

**問：提交後 status 持續為 `pending` / `running`。**
答：判題於背景執行，請檢視**視窗 A** 之伺服器日誌。常見原因為 `yhlib/cs3060701` 未 pull，或 Docker 未啟動，導致判題容器無法啟動。

**問：程式正確卻判為 `WA`。**
答：輸出比對會正規化行尾空白與結尾空行，但其餘內容仍須完全一致。請以 `output_log` 比對期望輸出與實際輸出；另須注意判題以啟發式方式尋找可執行檔（擷取 `build/` 下第一個可執行檔），結構較複雜之專案可能須調整 `internal/judge/judge.go` 之 `runScript`。
